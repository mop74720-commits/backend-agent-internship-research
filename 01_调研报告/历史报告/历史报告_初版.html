01 结论与阅读方式

建议采用“一条扎实后端主线 + 一个能可靠完成业务任务的Agent项目”。技术广度围绕真实问题展开；两个项目分别提供后端机制与Agent效果的深度证据。

本次按中国大陆大厂后端实习、Agent应用/平台工程实习调研；SSP作为高竞争力校招目标单独分析。没有用户当前语言、毕业年份、实习窗口和可投入时间，因此暂按Java后端主线、Python Agent方案设计；如果已有Go基础，应保留主语言，迁移业务和验证方法。

资料覆盖招聘JD、成功者简历片段/履历、候选人面经、B站/知乎内容，以及项目源码。招聘职责用于判断“做什么”；面经用于判断“怎样被考”；履历用于观察“成功者有什么证据”；专业观点用于补充方法。四类证据不互相冒充。

本轮样本中，与拟定能力组合直接对应的岗位描述包括百度AI开放平台、字节计算Agent、飞书Agent/RAG与百度Agent Harness。它们共同把语言基础、业务工程与Agent执行质量联系起来。[JD08][JD09][JD11][JD14]

把别人的亮点转成你的实验

  • 别人写“索引优化”：你需要保留查询、数据分布、执行计划、优化前后相同负载的结果。
  • 别人写“解决重复消费”：你需要复现消费提交成功但ACK丢失，再证明业务没有重复扣减或释放。
  • 别人写“Agent效果提升”：你需要公开评测定义、样本来源、基线和失败类型，说明成本是否同时上升。
  • 别人写“开源贡献”：你需要可定位的PR、问题讨论、测试和维护记录，而不只是一条GitHub链接。

09 项目A：资源预约与履约后端

拟定项目：ReserveFlow。让社团/实验室/小团队预约有限资源，在高峰、重复请求和故障下仍保持正确状态。首版资源按离散时段和容量建模，不实现真实支付。

选择这个场景，是因为容量、过期、改期、审批和重复消息都有可检查的业务结果；也能为Agent提供真实工具。它是本报告设计建议，不是已有部署成果。若拿不到真实用户反馈，必须标为自建业务实验系统。

范围与技术

Java + Spring Boot + MyBatis/JPA二选一 + MySQL + Redis + 一个MQ（RabbitMQ或RocketMQ择一）+ Docker Compose + CI。采用模块化单体，至少区分资源/时段、预约、权限、消息派发、审计；前端只做到能操作与演示。模型与图表使用的版本在实现时固定。

模块必须落地展示材料
容量与状态机每时段容量；HELD转CONFIRMED/EXPIRED/CANCELLED；确认后可按规则取消状态图、事务边界、竞争测试
幂等API租户+操作+幂等键唯一；绑定请求hash；同键异参拒绝重复提交、响应丢失后的查询与重试
改期一个业务命令内验证旧预约和新容量；成功原子迁移，失败保留旧预约新时段无位/并发改期/版本冲突实验
异步事件业务与Outbox同事务；派发至少一次；Inbox去重记录与消费者本地业务变化同事务发布后崩溃、ACK丢失与恢复记录
缓存与热点读缓存、按租户限流、失效策略；MySQL为权威状态缓存失效/Redis不可用时的降级曲线
权限与审计租户隔离、对象所有权、管理员范围、每次写前校验越权测试、审计关联task_id/action_id

三个核心正确性条件

  • 同一资源时段：可用容量 + 有效预占容量 + 已确认占用容量 = 配置总容量；所有计数不能为负。到期但尚未清理的预占仍占用容量，清理只释放一次。
  • 状态变更与对应容量变更在同一数据库事务中完成。HELD确认不再次扣容量；取消/过期只有赢得条件更新的执行者释放容量。
  • 确认与过期用数据库时间及状态/版本条件处理竞争。连续时长可能覆盖多个离散槽；改期按固定顺序锁定全部受影响时段，减少死锁，失败时旧预约仍有效。

MySQL锁定读和事务是实现参考；Outbox与消息重投用于解释故障模型。Inbox只能保护同事务内的本地变化，外部副作用需独立幂等机制。不能仅凭一个Redis锁宣称整个业务“绝不会重复”，也不将Outbox/Inbox表述成所有外部副作用端到端exactly-once。[DOC07][DOC08][DOC09][DOC10]

可复现验收

  • 正确性：同一key重复请求、并发抢同一容量、确认/超时并发、取消重试、改期失败、越权请求都检查数据库终态。
  • 故障：提交后响应丢失；发布消息后未标记已发布；消费者提交后ACK丢失；缓存不可用；调度器暂停后恢复。
  • 性能：先测纯DB基线，再加缓存与异步；固定机器、数据量、负载分布、并发或到达率、预热和测量时长，报告吞吐、p50/p95、错误率及资源。
  • 范围：至少完成两条能讲到代码、数据库与监控的深链路。分库分表、微服务拆分只有在测试暴露明确问题时再引入。

10 项目B：可靠的业务执行Agent

拟定项目：CampusOps Agent。把自然语言的多约束需求转成可确认、可恢复、可审计的资源协调任务。先实现单Agent，让模型选择下一步检索或工具；确定性的业务约束由服务端执行。

示例任务：为8人讨论寻找下周连续两小时、可投影且与成员已有安排不冲突的场地；比较方案并解释规则，用户批准后预约。若候选方案尚未预占或HELD已过期，提交时可能需重新提供备选；有效HELD的容量不能再被他人占用。第二类任务是跨多个已有预约查冲突、改期或取消，并处理失败。所有成员日程与业务数据先使用授权或自建数据。

与单次API封装的差别，在于存在跨工具的信息收集、状态随时变化、执行后果、批准与恢复，以及独立验收。Agent的必要性仍要通过对比表单/固定工作流证明；若固定工作流已足够，就把Agent限制在有动态分支的部分。[DOC01]

实现路线

推荐Python + FastAPI + LangGraph；若Java较熟且时间紧，可用Java Agent路线，能力要求不变。检查点首版可采用持久化SQLite单工作进程；需要多实例时再换PostgreSQL等持久化后端。检索组件只选一个，必须支持租户/文档权限与版本过滤；同时保留关键词与向量检索基线。[DOC04][PRO04]

环节设计要求
理解与规划结构化约束、缺失信息追问、有限步数和预算；区分只读查询与产生副作用的动作。
RAG与规则文档解析、分块、版本、权限、引用；检索用于解释规则，最终可预约性由业务API判断。
工具层严格schema；服务端绑定用户身份；读写工具分开；确认/取消/改期是业务原子命令。
批准审批绑定用户/租户/唯一action_id/操作/参数hash/业务版本/有效期；业务提交与审批消费同事务。参数或权限变化重检；不得换幂等键重放同一批准。
执行与恢复执行前取得并持久化action_id/幂等键；超时先查结果，再用原键重试；恢复旧检查点也不能跳过授权。
返回与观测返回可核对预约ID和状态；关联task_id、工具调用、文档版本、耗时、tokens和失败原因。

MCP可以作为工具接口规范；不需要把每个普通函数都包装成MCP。接口协议、编排框架与业务授权是三个不同层次。调用工具与“正确完成任务”也不是同一件事。[DOC05][DOC06]

首版明确排除

  • 真实金钱支付、任意宿主机命令、未经授权外部账号操作。演示系统只调用自己可控的业务接口。
  • 为了名词广度加入多Agent、自训练模型、四种向量库或Kubernetes。需要扩大时，先拿出基线不足的证据。

研发效能备选

如果能取得真实代码仓库和缺陷样本，可把B换成“代码问题定位与测试Agent”：检索代码/文档、分析调用链、提出补丁、在隔离环境运行测试。验收以隐藏测试和补丁正确性为主；这更贴近JD10，但比业务执行场景更难控制范围。只选一条做深。

11 Agent评测与项目验收规格

建议第一版建立100-150条领域任务，属于个人项目规划规模，不是招聘标准。按场景家族/文档来源/业务模板拆分开发、验证、隐藏测试，避免同一题改几句话同时进入训练调优与测试。可从60/20/20比例起步，小样本必须报告局限。

任务组至少覆盖的变化判定依据
查询与规则解释缺条件、跨文档、无答案、旧规则、表格授权范围内的证据与引用；必要时澄清/拒答
资源协调多约束、无可用资源、时间冲突、动态占用最终方案符合硬约束与用户选择
写操作预约/确认/取消/改期，重复提交与用户拒绝数据库最终状态、容量与审批记录
恢复工具超时、响应丢失、服务重启、模型错误参数原任务可恢复，副作用不重复，错误明确
权限与输入干扰跨租户、撤权、过期批准、检索文档含恶意指令无未授权读写；合法请求也不能被全部拒绝
长期与预算多轮任务、上下文压缩、成本超限、工具循环保留关键约束；预算内终止或交接

比较对象

  • B0：规则表单/确定性工作流。用来测试Agent是否有真实增量。
  • B1：关键词或向量RAG + 固定工具路由。用来分离检索与自主规划收益。
  • B2：受约束的单Agent + 持久化 + 工具可靠执行。作为首个完整方案。
  • 仅在B2暴露明确问题时，研究rerank、记忆压缩、模型路由或多Agent；每次只改变一个主要因素。
指标计算与注意事项
合法任务成功率满足全部硬约束并达到预期终态的试验数 / 合法任务试验数；失败包含超时、错误写入和预算耗尽。
重复运行稳定性每条任务运行3次，报告每题成功次数分布与宏平均；3次试验不等于3个独立任务。
未授权/重复副作用分别记录次数、触发场景与可恢复性；观察到0次只是该测试集结果，不是永远安全保证。
RAG质量Recall@k、引用准确/支持率、无答案处理；明确标签和证据粒度，避免把检索命中等同任务完成。
成本与延迟固定模型版本、语料版本和预算；报告每任务成本、每成功任务成本及p50/p95，失败成本也计入。
拒绝质量非法任务正确拒绝率与合法任务误拒率分列，防止“全部拒绝”刷安全指标。
人工与裁判确定性约束用程序评分；语义输出用人工抽检或经校准的裁判，不只依赖模型给自己打分。

评测框架依据官方工程文档，具体任务集、指标阈值与拆分由本报告为项目设计。每项结果都应带样本数和环境；可以在取得基线后设个人改进目标，不能把任意80%或90%叫作SSP门槛。[DOC02][DOC03][PRO06]

对外作品应包含：冻结任务集版本、评测脚本、原始JSONL结果、指标报告、失败分类、至少一次消融和一段恢复演示。比“做了RAG+MCP+多Agent”更容易让面试官判断真实贡献。
